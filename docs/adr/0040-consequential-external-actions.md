# ADR-0040: Keep consequential external actions in the rule taxonomy

## Status

Accepted for [#234](https://github.com/CtrlCarlitos/agent-guardrails/issues/234). The first increment applies to the four named P6 rules. Changes to command coverage and a dedicated broker require separate review.

## Context

Guardrail can see a command that spends money or changes a remote resource even when the credential stays in a keychain, kubeconfig, or inherited environment. The judgment question is which actions need a human decision. [ADR-0038](0038-per-plane-agent-credentials.md) addresses the separate identity question. The scoped GitHub bot and repository rulesets bound what its token can do. The accepted classic PAT still permits collaborator writes and can overwrite Actions secrets in repositories it can reach. Publication and other permitted writes remain judgment decisions. Other services have their own credential boundaries.

| Existing control | What it covers |
| --- | --- |
| `CapabilityExternal` | The Engine returns `capability-external` Ask for contracted native tools such as artifact and scheduling tools. This branch returns before command, path, and Overlay evaluation. The adapter must establish that the host dispatches the call and exposes enough input to classify it. [Capability dispatch](../../internal/engine/evaluate.go) |
| [ADR-0018](0018-external-tier-never-relaxed-by-night-mode.md) and `policy.NeverRelaxable` | External, web search, unclassified native tools, machine power, and network-stack asks stay in force overnight. `NeverGrantable` also excludes these IDs from standing command grants and the current Codex exact-action broker. Overlay waiver filtering uses a separate set. [Grant policy](../../internal/policy/grants.go) · [Overlay merge](../../internal/policy/merge.go) · [Exact-action eligibility](../../internal/engine/action_grant.go) |
| Shell rules | Existing P6 IDs cover publishes, deployments, remote cluster mutations, and metered infrastructure mutations. GitHub release changes also use `P6.publish`. Git and GitHub rules separately cover protected pushes, remote ref deletion, force pushes, repository administration, protection changes, merges, and workflow control. These shell IDs are outside the current `NeverRelaxable` set. [Credentialed CLI rules](../../internal/engine/rules_credentialed.go) · [Git rules](../../internal/engine/rules_git.go) · [GitHub rules](../../internal/engine/rules_gh_porcelain.go) |

## Proposed decision

Keep `CapabilityExternal` for mediated native calls and extend the same per-call approval principle through the existing shell rule taxonomy. A parsed shell action keeps its command capability and flows through command, path, secret, egress, and Overlay checks. A stronger Deny still wins. Among competing Asks, a protected Ask must survive arbitration and the subsequent approval path, including when an unrelated Ask comes first in a compound command.

1. Start with `P6.publish`, `P6.deploy`, `P6.cluster-mutate`, and `P6.cloud-mutate`. Preserve their IDs and place them under the shared non-relaxation policy. Require fresh human approval for these matches across Night, command grants, cached approvals, and authorized Overlay waivers. Check the existing waiver and grant inventory before rollout, and surface entries that become ineffective through operator diagnostics. Existing Git and GitHub IDs retain their current posture in this first increment. Review those IDs individually, especially `P2.git-push-protected`, which covers both protected branches and release tags.
2. Keep CLI grammar in reviewed built-in classifiers. Reuse the #235 verb tables, wrapper handling and parsed arguments. Table entries should identify the tool, operation and rule ID. Keep target and dry-run predicates with the CLI grammar. Verify that each dry-run exception actually suppresses the relevant external effect. Use review and fixtures to cover read twins, wrapper forms, and Windows PowerShell as well as POSIX shell input.
3. Treat scope as evidence for a rule. A repository cwd alone says nothing about the remote owner, registry, cluster, account or project. Preserve positively established local and read-only cases. An implicit or unresolved destination for a recognized consequential operation keeps its Ask. Validate current local exceptions, including whether a Kubernetes context name can establish locality. Ordinary branch and PR workflows remain governed by the existing GitHub and delivery rules.
4. For a known credentialed family with unbounded write verbs, ask on unknown operations and explicitly identify the supported read forms, following the existing cloud classifier's shape. For an entirely unrecognized executable, retain [ADR-0036](0036-unmatched-commands-and-safe-control-allow.md)'s parsed-command default. The Engine lacks a reliable general signal that an executable carries credentials. Use least-privilege credentials and provider-side controls for unclassified traffic and for budgets. Classification can flag known spending operations even though it cannot predict usage or measure spend.
5. Use a fresh host approval where the plane can present one. [ADR-0035](0035-hosts-that-answer-asks-themselves.md) continues to require an operator handoff when the host answers its own asks. Codex presents a block and operator handoff under [ADR-0014](0014-codex-native-hooks-and-blocked-asks.md). A later broker proposal could support one verified execution bound to the exact action, session, repository, working directory, destination when resolved, and a short expiry with atomic consumption. That would require a dedicated authorization path because the current exact-action broker rejects `NeverGrantable` IDs. WebAuthn is a candidate for that path.

## Alternative considered

A first-class Effect capability would give native and shell actions a common label, with a natural place for scope and billing metadata. It would still require CLI grammar to decide which particular invocations publish, mutate, or spend. Making it an exclusive capability risks skipping independent checks, as the current native External branch does. Making it an additional attribute would preserve those checks but require new arbitration, adapter and audit plumbing while retaining the rule IDs for existing consumers. Revisit that option when a use case requires effect metadata across multiple families, such as an operator policy on verified destinations.

## Stability and verification

The [stability policy](../stability-policy.md) permits internal API changes, additive fields and stricter rules. Keep the three public verdicts, adapter protocols, severity ordering, existing rule IDs and config schemas. The proposal tightens when existing IDs can be relaxed. Document that change in the CHANGELOG and operator guidance, with an explicit review of its effect on existing Waivers and grants. Repurposing an existing stable ID or changing the meaning of a stable config key would require the breaking-change process.

After approval, verify with fixtures for a publish, release deletion, remote cluster mutation, metered cloud operation, read twin and supported dry-run. Include a compound command with a competing Ask and a separate case with a stronger Deny. Verify attempted Night, waiver, grant and approval-reuse paths, plus per-plane Ask handling on supported hosts. Record actual Windows and Linux evidence. Codex hosted tools and `write_stdin` bypass pre-hooks, and child mediation remains upstream-blocked. Coverage claims apply to calls the plane actually dispatches before the effect.
