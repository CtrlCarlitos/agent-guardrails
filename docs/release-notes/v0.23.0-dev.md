# v0.23.0-dev

Since `v0.22.0-dev` (40 changes). Written for the operator: what changed about
what guardrail stops, and what now asks that did not before.

If you read one section, read **What now asks that did not before** — that is
the part you will notice in a working session.

---

## The serious fix

**`rm -rf /` was allowed on Windows.** It needed no wrapper, no redirect and no
container — the single most basic destructive command in the corpus, and on a
Windows host it passed.

A Bash command's paths are POSIX (`/etc`); Windows paths are not
(`C:\repo`). Guardrail judged the first using the rules for the second, and
Windows reads `/etc` as a *relative* path — so every absolute POSIX path was
silently treated as "inside your repository", landed there, and was allowed.
`/` became the repository itself, which is why deleting it read as deleting
your own working tree.

This is fixed: a path is now judged in the coordinate system it was written in,
translated once and explicitly. `/c/repo/x` still means `C:\repo\x`, so
ordinary Git Bash work is untouched, and `/tmp` still behaves as your temp
directory. **29 adversarial cases closed**, including every wrapper form
(`bash -c`, `busybox`, `chroot`, `setsid`, `docker`, `ssh`).

Linux and macOS were never affected — the two path systems agree there.

## What now asks that did not before

Guardrail asks instead of blocking, so each of these is a prompt, not a wall.

**Commands that act with credentials you never see.** `npm publish`,
`docker push`, `kubectl apply`, `terraform apply`, `vercel --prod` and their
families act with real authority — the token is in a keychain, a kubeconfig, or
an inherited environment — and none of them touch your working tree, so nothing
else noticed them. Reads stay free: `kubectl get`, `terraform plan`,
`docker pull`, `npm view`. `--dry-run` stays free. A local Kubernetes context
(`kind-`, `minikube`, `docker-desktop`) stays free; an *unstated* context asks,
because "I cannot tell which cluster" should not resolve to "it is fine".

**GitHub commands that change your repository's protections or your account.**
Previously only the `gh api` spelling was mediated, while the ordinary
porcelain — the spelling an agent actually reaches for first — was not:

| Command | Now |
|---|---|
| `gh repo delete` | **blocked** |
| `gh secret set/delete`, `gh variable set/delete`, `gh repo edit`, `gh ruleset …` | asks |
| `gh repo archive/rename/transfer` | asks |
| `gh pr merge` | asks |
| `gh release create/delete/edit/upload` | asks |
| `gh workflow run/enable/disable` | asks |
| `gh auth refresh -s …`, `gh auth login --scopes …`, `gh auth switch` | asks |
| `gh auth logout` | asks |
| `gh ssh-key add/delete`, `gh gpg-key add/delete` | asks |

Reads are all still free — `gh pr list`, `gh secret list`, `gh run view`,
`gh auth status`. Plain `gh auth login` and `gh auth refresh` stay free too:
re-authorizing scopes a token already has is not widening them, and prompting
for it is how you learn to click through the prompts that matter.

**Machine power control.** `shutdown`, `reboot`, `systemctl poweroff` and their
PowerShell equivalents ask in every shell — and this one is **never** relaxed
overnight, because losing the machine at 3am is not a routine ask.

**Go toolchain commands** are classified per subcommand, so `go build` and
`go test` stay free while the ones that reach the network or write outside the
tree do not.

## New: authorize one exact command

There was a deadlock. Some prompts cannot be cleared from chat, and the usual
endgame was that you ran the command outside guardrail — which meant the single
most consequential action in the session was the only one with **no audit
record**.

```sh
guardrail approvals grant --repo <path> --rule <id> --command 'git push origin main'
guardrail approvals list --grants
guardrail approvals revoke --repo <path> --rule <id> --command 'git push origin main'
```

Deliberately narrow:

- **Exactly one command**, matched literally. No wildcards. `git push origin
  HEAD:main` is *not* covered by a grant for `git push origin main`, even
  though both push the same branch.
- **One use by default.** `--uses N` raises it. Spent when used.
- **30 minutes by default**, capped at 24 hours.
- **Never for outward reach.** Web access, external tools and unknown tools can
  never be granted, and neither can guardrail's fail-closed backstops.
- **Refused unless you are at your own terminal**, and it shows you the exact
  command text — twice, once quoted, so trailing spaces and tabs are visible
  before you approve.

Both ends are audited: issuing a grant and using it. See
[ADR-0027](../adr/0027-operator-issued-grants-authorize-one-exact-command.md).

## Faster on Windows

A **resident daemon** now handles hook traffic over a named pipe, so evaluating
a tool call takes about a millisecond instead of paying process-start and
antivirus-scan cost every time. This was the difference between usable and
timing-out on Windows.

Also on Windows: MSYS mount handling, inspectable Codex wrappers, and clearer
messages when something degrades ([ADR-0024](../adr/0024-windows-agent-experience-mounts-and-wrappers.md),
[ADR-0025](../adr/0025-persistent-daemon-broker-windows.md)).

Two session-lock fixes removed spurious contention failures under concurrent
sessions.

## Seeing what the guard is doing

**`guardrail audit --verdicts`** reports what was *decided*, per rule — not
just that guardrail ran.

**`guardrail doctor`** gains a `credential posture:` section. It warns when the
`gh` login carries administration-shaped scopes, when more than one account is
logged in, or when your kubectl context is not a known-local cluster, and names
credential environment variables **by name only** — never their values. New:
[docs/operator-hardening.md](../operator-hardening.md), which is the setup for
running agents under a credential that simply lacks the dangerous authority.
That is the strongest control available, and it is not one guardrail can give
you.

**Clearer prompts.** A prompt now says *which* approval path applies. Agents
were reading "request authorization" as "go find the technical approval
mechanism" and hunting for URLs and daemons that do not exist for that rule.

## Direction: settings files are going back to you

[ADR-0028](../adr/0028-settings-files-are-user-owned-hooks-only.md) records a
decision you will see land over the next releases.

Guardrail currently writes a large block of permission rules into each plane's
settings file — 243 entries in Claude's, 251 in OpenCode's. An audit found that
this is a **second, drifting copy** of rules the engine already enforces:
OpenCode's copy added nothing at all, and Claude's added four families out of
243. Meanwhile the copies fell 24 and 8 entries behind, and could not be
cleanly removed when you disabled the integration.

So they are going away. Settings files return to **your content plus
guardrail's hook entries**, and policy lives in one place. Antigravity has run
this way since ADR-0008 — no rules in settings at all — which is the proof the
decision rests on.

Two consequences stated plainly:

- **While the engine is unreachable, those planes are unguarded.** Previously
  the settings rules covered some of it, silently and out of date. This release
  adds the loud version: if the engine cannot start, your session says so
  explicitly instead of quietly continuing.
- **Codex is an exception and keeps its rules.** Its hooks do not currently
  dispatch on Windows (openai/codex#24453), so those rules are its only
  enforcement. They stay until that is fixed.

Nothing in this release removes anything from your settings files yet.

## Also

- Overlay rules can tighten a built-in rule but never loosen it, and equal
  verdicts report the built-in ([ADR-0026](../adr/0026-built-in-and-overlay-verdicts-combine-by-severity.md)).
- Deny verdicts carry machine-readable metadata for tooling.
- The settings-rule generator was corrected for both Claude's and OpenCode's
  pattern matchers, which disagree with each other; a test now proves each
  generated rule matches the command it exists to stop.
- Codex hook failures are reported separately from policy denials, so a broken
  hook no longer looks like a refusal.
