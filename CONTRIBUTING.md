# Contributing

Thanks for looking at agent-guardrails. This page is the map: how to build and
test, the house rules, and where each kind of change lives. Vocabulary is in
[`CONTEXT.md`](CONTEXT.md), decisions are in [`docs/adr/`](docs/adr/), the
operator runbook is [`docs/OPERATIONS.md`](docs/OPERATIONS.md), and the shape
of the project is in the README section "Working on it".

What may change and what may not: [`docs/stability-policy.md`](docs/stability-policy.md).
Read it before touching a verdict, an exit code, the Overlay or Operator config
formats, or the audit log.

## Build, format, vet, test

Go `1.26` (`go.mod` says `go 1.26.0`). Run from the repository root:

```
go build ./...
gofmt -l .            # must print nothing
go vet ./...          # must be clean
go test ./...         # must be green
```

`make check` bundles test, vet, the adversarial corpus and a gofmt check (and
the `install.sh` harness on Linux). `make` is optional; every target is a thin
wrapper over the commands here.

A change is ready to push when all four are green on **Windows and on Linux**.
CI runs Ubuntu, macOS and Windows, but it runs only a name-filtered slice of
the suite on Windows, so a Windows-only problem can hide from CI (#332 did).
Checking both locally is the rule.

### Linux from a Windows machine (WSL)

Write the script to a file (an inline `bash -c` inherits the Windows `PATH` and
breaks), then run the file:

```bash
#!/bin/bash
export PATH=/usr/local/go/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export GOCACHE=/tmp/aghome/.cache/go-build GOMODCACHE=/tmp/aghome/go/pkg/mod
mkdir -p "$GOCACHE" "$GOMODCACHE" /tmp/.git
cd /mnt/c/<path-to-your-checkout> || exit 1
go vet ./... && go test ./... -count=1
```

```
MSYS_NO_PATHCONV=1 wsl.exe -d Ubuntu-24.04 -- bash /mnt/c/<path>/script.sh
```

Strip NUL bytes from the output (`| tr -d '\0'`). Do not override `$HOME`: a
home-dependent adapter test then fails and looks like a real regression. The
`mkdir /tmp/.git` mirrors a CI step that guards the temp-root repo-discovery
boundary. The Go toolchain must be installed in the distro at
`/usr/local/go`.

### The adversarial corpus

`test/adversarial/corpus.json` is the 300+ case corpus of hostile commands and
the verdict each must get. Run it alone with:

```
go test ./test/adversarial/ -v
```

(`make adversarial` is the same command.) The per-plane contract fixtures
(recorded real hook payloads with the verdict, rule and projected paths pinned)
run with `go test ./test/ -v`; refresh golden files deliberately with
`go test ./test/ -run Golden -update` and review the diff. When you add a rule,
add the hostile spellings you can think of to the corpus.

### Installer harnesses

Only when you touch `install.sh`, `install.ps1` or `scripts/build-dist.sh`:

```
VERSION=v0.0.0-ci ./scripts/build-dist.sh
DIST=dist VERSION=v0.0.0-ci pwsh -File test/installer/install_ps1_test.ps1   # Windows
bash test/installer/install_sh_test.sh                                        # Linux/WSL
```

`dist/` is gitignored; remove it afterwards.

## House rules

- **TDD.** The failing test comes first. Write it, watch it fail for the right
  reason, then fix. Say in the PR what the red run looked like.
- **Root-cause, never re-baseline.** A red check gets fixed at its cause. Do
  not make it green by changing the expectation.
- **One PR per issue.** Never stack a PR on another PR's branch: when the base
  merges, GitHub closes the stacked one and it cannot be retargeted.
- **Conventional commits** with the issue number, for example
  `fix(engine): recognise the canonical egress action in any flag order (#126)`.
  No attribution trailers (no `Co-Authored-By` or "generated by" lines).
- **Stage explicit files.** `git add <path>`, never `git add -A` or `git add .`.
- **No force-push.** To recover a bad branch, push a fresh one.
- **A Windows-only test is named `TestWindows...`.** CI's Windows job selects
  tests by name (`-run 'Windows|BOM|...'`) and by package list in
  `.github/workflows/ci.yml`; a test that matters only on Windows is invisible
  otherwise. Add the package to that list when you add the test.
- **Measure before asserting.** State an engine verdict, an exit code or a test
  result in an issue or PR only after running it. Other people plan against it.
- **A deny must say what to do next.** If a denial gives the agent no
  alternative, that is the bug ([`docs/error-message-discipline.md`](docs/error-message-discipline.md)).
- **Changelog.** A change to shipped behaviour adds a bullet under
  `## Unreleased` in [`CHANGELOG.md`](CHANGELOG.md), in the section for its
  theme.
- **PR body.** State the root cause and what you verified on each OS.
- **Squash-merge** once green; the branch is deleted on merge.

### Rules enforced on agents

If an AI agent works on this repository through a plane that guardrail
mediates, the guard applies to it, and these are not optional:

- A shell command whose interpreter literal mentions `guardrail` together with
  `night`, `setup`, `plane`, `operator` or `recover` is denied
  (`P5.self-config`). Put the script in a file and run the file; edit sources
  with the editor tool.
- `git push --force` is denied (`P1.git-push-force`). Use a fresh branch.
- Writes to the installed guardrail binary and to plane configuration are
  denied; use `guardrail update` and `guardrail plane enable`.
- `AGENTS.md` and `CLAUDE.md` at the repository root are placed by the
  operator, not by agents.

## Where a change goes

- **A rule change.** Engine rules are in `internal/engine/` (shell rules in
  `rules_*.go`), policy data in `internal/policy/`. Add the failing test in the
  same package and the hostile spellings to `test/adversarial/corpus.json`.
  If the change alters what a plane's adapter emits, update the fixtures under
  `test/fixtures/<plane>/`.
- **A new MCP family.** One entry in the registry in
  `internal/planecontract/mcp.go` (`MCPToolSpec`: family, tool, capability, the
  path argument names), with tests in `mcp_test.go`
  ([ADR-0017](docs/adr/0017-mcp-family-registry-and-projection.md)).
- **A new plane.** The plane's tool contract in `internal/planecontract/`,
  its adapter in `internal/adapter/`, its generated config in
  `internal/genconfig/`, and recorded payload fixtures in `test/fixtures/`.
  Read [ADR-0001](docs/adr/0001-hybrid-enforcement-model.md),
  [ADR-0002](docs/adr/0002-single-go-binary-subcommand-adapters.md) and one
  existing adapter first.- **An ADR.** Write one when a change alters a trust boundary, the operator's
  authority, a plane's enforcement model or a user-visible contract. Add
  `docs/adr/NNNN-short-title.md` with the next free number (list the directory), a `Status`
  line, and the context and decision in prose. Amend an earlier ADR with a status note rather than rewriting it.
- **Checking that a change did not break another plane.** `go test ./...`
  covers every plane's adapter and fixtures; then run `guardrail doctor` and
  `guardrail selftest` from the built binary.

## Filing an issue

Use the repository's issue tracker. Include the command or tool call, the
verdict you got (`guardrail audit` shows the `rule_id` and `reason`), the verdict
you expected, the plane and OS, and `guardrail doctor` output. For a security
problem do not open a public issue; follow [`SECURITY.md`](SECURITY.md).
